## 4. Recipe Selection

**Recipe: AZCLI**

**Rationale:**
- Single Azure resource — full IaC tooling (azd/Bicep) is disproportionate
- Deploying into a **pre-existing** resource group (`Sandbox`), which AZCLI targets
  directly without the resource-group-scope workarounds azd requires
- SWA's native GitHub integration generates the CI/CD workflow itself, so there is
  no infrastructure for azd to add
- User explicitly selected this option

> **Region note:** Static Web Apps is **not offered in `southcentralus`**. SWA content is
> served from a global CDN, and the resource location only selects the region for
> managed-Functions backends. A resource group's location is metadata only and does not
> constrain the regions of resources inside it, so creating the SWA in `westus2` inside
> the `southcentralus` `Sandbox` group is valid and has no effect on latency for this app.

**Static role verification (Step 5):** N/A — no Bicep/Terraform RBAC assignments in this
deployment. SWA Free tier uses a deployment token held as a GitHub Actions repo secret;
no managed identity or role assignments are provisioned.

**Unit tests:** Skipped at user's explicit request ("skip running the tests because they're
not fully functional"). Tests are excluded from the published site by
`staticwebapp.config.json`, so this does not affect the deployed artifact.

**Pre-existing artifacts found (not authored by this workflow):** `deploy.sh` and `steps.md`
both default to `RESOURCE_GROUP=rg-weatherview`, not the requested `Sandbox`. `deploy.sh`
also calls `az group create` and offers a `--destroy` mode that deletes an entire resource
group. To avoid any risk to other resources in the shared `Sandbox` group, deployment will
invoke `az staticwebapp create` directly rather than running `deploy.sh`.
